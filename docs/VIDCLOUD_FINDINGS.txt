6. video-script.js  -  OBFUSCATION ANALYSIS
--------------------------------------------------------------------------------
Size: 648,311 bytes on 14 lines (one gigantic line).
Obfuscator: javascript-obfuscator (obfuscator.io) with
  * a bytecode/VM-style dispatch loop (switch over opcodes, custom stack,
    "vmd_b2fe1c" sandbox object, trap/scope records with _$Y40KkE style keys)
  * a rotated, base64-encoded string table (function vms() -> const X6=[...])
  * RC4-style string decoders: vmn(index) and vme(index, key) - base64 decode
    then a KSA/PRGA XOR pass with a per-call key string
  * self-defending arithmetic guard: an IIFE at the top rotates the string array
    until a checksum expression equals 0xa229f (anti-tamper)
  * global anti-debug: redefines Function, window, document, fetch, CryptoJS,
    Hls, shaka, etc. via Object.defineProperty getters/setters

Because of this, plain grep for "decrypt", "AES", "enc_video_url", "mpd",
"cloudfront" returns ZERO useful hits. Static reading was a dead end.

8. THE BREAKTHROUGH  -  RUNTIME HOOKING
--------------------------------------------------------------------------------
Static analysis was blocked, so the page was executed for real.

Tooling constraint: no installs were allowed. A Chromium binary already existed
in the pre-populated Playwright cache:

  ~/.cache/ms-playwright/chromium-1148/chrome-linux/chrome
  ~/.cache/ms-playwright/chromium_headless_shell-1148/chrome-linux/headless_shell
  -> "Chromium 131.0.6778.33"

Method
------
1. Save the page locally, rewrite the relative script tag to an absolute URL so
   it still loads from the origin:
      src="video-script.js?v=102"  ->  src="https://vidcloud.eu.org/video-script.js?v=102"
2. Inject a hook BEFORE the player script runs, wrapping CryptoJS:
      - CryptoJS.AES.decrypt / .encrypt
      - CryptoJS.enc.Utf8.stringify
      - CryptoJS.PBKDF2
   Each wrapper records {arguments, return value} into window.__LOG.
   A polling setInterval waits for window.CryptoJS to appear (crypto-js is
   loaded from a CDN and may arrive after the inline hook).
3. After 12-20 s, dump window.__LOG into a <div id="__DUMP"> as JSON.
4. Run headless and read the DOM:
      headless_shell --headless --no-sandbox --disable-gpu \
        --disable-dev-shm-usage --autoplay-policy=no-user-gesture-required \
        --virtual-time-budget=40000 --dump-dom file:///.../page_hooked.html

Result: four captured calls, and the whole scheme fell out:

  [0] AES.decrypt
      arg0 = "zz6m5QqWttpHqD+mR7HRfW7GGw/WCgFN2l0NmHZy/tdsQJYc..."  (the blob)
      arg1 = "5237406b503423784c39216d51322476"                     (THE KEY)
      arg2 = [object Object]                                        (config)
      res  = 68747470733a2f2f62756e6e792d63646e2d...  (hex of the URL)

  [1] Utf8.stringify
      arg  = <same hex>
      res  = https://bunny-cdn-qbg-s7.testwave.cc/08120d005a0c...jpeg?Policy=...

  [2] AES.decrypt
      arg0 = "4BloTF1TnAw/nwFoOrwx5A=="   (the #enc_drm_type field)
      arg1 = "5237406b503423784c39216d51322476"
      res  = 636c6561726b6579

  [3] Utf8.stringify
      res  = clearkey

So: one static key decrypts every #enc_* field on the page.

Why arg2 shows as "[object Object]": CryptoJS.AES.decrypt takes
(message, key, cfg) and the site passes a config object (mode/padding). Because
the IV was not visible in the log, it was derived independently:

  AES-CBC:  P0 = D(C0) XOR IV   =>   IV = D(C0) XOR P0
  With C0 = first 16 bytes of the ciphertext and P0 = "https://bunny-cd"
  (known plaintext prefix, since every media URL starts with "https://bunny-cd"):

      IV = 5433216e573824715a3540724b312370  =  "T3!nW8$qZ5@rK1#p"

  This is a human-readable 16-char ASCII string, which is exactly how the site
  author hardcoded it. Using that IV, the full 784-byte ciphertext decrypts
  cleanly to a 768-byte URL with no padding garbage.

Failed approach worth recording (do not repeat)
-----------------------------------------------
Before hooking, ~1400 AES combinations were brute-forced offline:
  keys: raw hex of the string, MD5/SHA-256 of the string, base64 text, hex text,
        MD5 of each ObjectId, MD5(blob+ObjectId), ...
  IVs:  zero, key-as-IV, first/last ciphertext block, ...
  modes: CBC, ECB, CFB, OFB, CTR, CFB8; with and without padding
Result: ZERO hits. The key is a raw 32-char hex string used as 16 BYTES
(bytes.fromhex), not as an ASCII passphrase, so no phrase-based derivation
(MD5/PBKDF2/EVP_BytesToKey) applies. The hook was the only reliable route.

RULE 0 - The PAGE also needs a User-Agent (different rule, different host)
--------------------------------------------------------------------------
  play.php with NO User-Agent header at all -> 403 Forbidden
  play.php with any UA string               -> 200

  Python's urllib sends no User-Agent by default, so
  urllib.request.urlopen(play_url) fails before decryption is even reached.
  The extractor therefore always sets one.

  Measured on play.php (no cookie needed, any non-empty UA works):

    (header absent)      -> 403
    python-urllib/3.12   -> 200
    python-requests/2.31 -> 200
    curl/8.5.0           -> 200
    Wget/1.21            -> 200
    Mozilla/5.0          -> 200

  This is a DIFFERENT rule from RULE 2 below, which applies to the CDN host and
  where a Chrome UA is actively blocked. Do not conflate them: play.php wants
  *some* UA, the media CDN wants *no* Chrome token.

RULE 1 - Referer is MANDATORY
-----------------------------
  no Referer                        -> 403 AccessDenied
  Referer: https://vidcloud.eu.org/ -> 200 / 206   <-- required
  Referer: https://google.com/      -> 403         (must be the site itself)

  The PHPSESSID cookie made NO difference (with and without it: 403 when the
  Referer was absent, 200 when present). So it is a pure Referer check, not a
  session check.

15. HOW TO RE-DERIVE EVERYTHING IF THE KEY EVER ROTATES
--------------------------------------------------------------------------------
If #enc_video_url stops decrypting (site pushes a new video-script.js):

  1. Fetch the page and note the current #enc_video_url blob.
  2. Confirm the expected plaintext prefix: every media URL begins with
     "https://bunny-cd" (or at minimum "https://").
  3. If you have the key, get the IV with:  IV = AES_dec(C0, key, IV=0) XOR P0
     (C0 = first ciphertext block, P0 = known 16-byte plaintext prefix).
  4. If you do NOT have the key: re-run the hooking recipe from section 8 -
     wrap CryptoJS.AES.decrypt before video-script.js loads and read the args.
     That is the fastest reliable way; static deobfuscation of this file is not
     worth the time.
  5. Expect the new key to be a 32-char hex string (16 raw bytes) and the IV to
     be a 16-char printable string, based on the current implementation style.

Sanity checks after any change:
  * decrypting #enc_drm_type must yield a short lowercase word ("clearkey");
    if it yields garbage, key or IV is wrong.
  * a correct decrypt of #enc_video_url ends with "&Key-Pair-Id=...".
  * a wrong key/IV gives binary garbage or a mangled "https://" prefix.
